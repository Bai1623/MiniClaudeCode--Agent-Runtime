# miniClaudeCode 科研与工程化演进路线图

更新时间：2026-08-22

## 1. 路线图目标

miniClaudeCode 下一阶段的目标不是继续堆叠功能，而是升级为：

```text
可复现、可评测、可审计的轻量级 Coding Agent Runtime
```

所有优化都应尽量回答三个问题：

1. 任务成功率是否提高。
2. token、耗时或工具调用成本是否下降。
3. 可靠性、安全性或可恢复性是否改善。

路线采用“评测驱动 + 工程护栏”的推进方式：先补齐可信观测和实验基线，再优化 Harness、Memory、并发与安全能力。未经实验验证，不优先引入向量数据库、复杂多 Agent、Web UI 或完整 MCP Server。

## 2. 当前基线与主要缺口

当前已经具备 AgentLoop、Tool Runtime、Planner-Executor-Evaluator Harness、Git Workflow、Memory/Context、unittest、mypy、ruff 和 CI 基线。

现阶段主要缺口：

- `compression.py` 已产生 `original_output_chars`、`kept_snippet_lines` 和 `snippet_truncated`，但 Trace 尚未完整记录，Harness report 无法得到真实统计。
- Trace 以工具调用为主，缺少模型轮次、token、缓存、停止原因和运行级汇总。
- Harness evaluator 主要依赖固定命令和测试文字检查，尚不能可靠证明需求已经完成。
- Planner 目前是确定性任务结构转换器，还不是自动规划器。
- ContextBuilder 只接入 CLI，尚未参与 AgentLoop 的上下文构建。
- 上下文压缩按消息数量和字符预算工作，未使用实际 token 和信息价值。
- Bash 和 workspace 安全仍以词法规则为主，尚无操作系统级文件与网络隔离。
- 缺少可重复运行、支持多 trial 和消融对比的 Coding Agent eval 数据集。

## 3. 核心实验指标

### 3.1 任务质量

- `pass@1`
- `pass@k`
- `pass^k`
- fail-to-pass 测试通过率
- pass-to-pass 回归保持率
- 任务级验收标准通过率

### 3.2 执行效率

- 输入、输出、cache token
- 单任务和单工具 P50/P95 耗时
- 工具调用总数与冗余调用率
- 工具输出压缩率
- 单次成功任务的 token、时间和可选成本

### 3.3 可靠性

- 工具错误率和错误类型分布
- repair 成功率与平均修复轮数
- checkpoint 恢复成功率
- 超时、基础设施失败与 Agent 失败的占比

### 3.4 上下文检索

- Recall@K
- Precision@K
- MRR
- 固定 token 预算下的任务成功率
- 被检索内容的实际使用率

### 3.5 安全性

- 攻击用例阻断率
- 安全命令误拦截率
- 每个任务的人工审批次数
- workspace、网络和凭证越界次数

## 4. 按顺序执行的小推进队列

状态约定：`[ ]` 未开始，`[x]` 已完成。默认一次“小推进”只处理第一个未完成项；若单项超出一个可审查提交，则拆成连续子任务，父项全部验收后再标记完成。

### 阶段一：可信可观测性

- [ ] 01. 补齐 Trace 压缩字段：记录 `original_output_chars`、`kept_snippet_lines`、`snippet_truncated`，修复 report 数据链路并补测试。
- [ ] 02. 对 Trace 输入预览做敏感字段脱敏；文件写入内容默认只记录长度、摘要或哈希。
- [ ] 03. 为 Trace 增加 `schema_version` 和结构化事件构建入口，避免生产端与消费端字段漂移。
- [ ] 04. 新增独立 `TraceSummary`，统计调用数、错误类型、重试、压缩率、P50/P95 耗时和慢工具。
- [ ] 05. 生成 `run_summary.json`，并让 Harness final report 复用同一份汇总逻辑。
- [ ] 06. 记录模型轮次的 API 耗时、`stop_reason`、输入/输出/cache token。
- [ ] 07. 扩展 `AgentRunResult`，统一记录完成、最大轮次、预算耗尽、拒绝、上下文超限和异常等终止原因。

### 阶段二：科研评测基线

- [ ] 08. 定义 `EvalCase` 数据结构：任务、fixture、成功标准、grader、预算和标签。
- [ ] 09. 实现结果 grader：fail-to-pass、pass-to-pass、预期修改文件、禁止修改路径。
- [ ] 10. 增加 no-op grader，避免未修改代码却因原测试通过而误判成功。
- [ ] 11. 实现隔离式 EvalRunner，每个 trial 使用临时仓库或独立 worktree。
- [ ] 12. 保存完整 transcript、tool trajectory、代码 diff、grader 结果和运行产物索引。
- [ ] 13. 支持同一 EvalCase 多次 trial，并保持每次运行相互隔离。
- [ ] 14. 汇总 `pass@1`、`pass@k`、`pass^k`、token、耗时、工具调用数和错误率。
- [ ] 15. 保存实验 manifest：Git SHA、模型、配置哈希、Python、系统、资源限制和超时。
- [ ] 16. 建立首批 8 至 12 个本地 fixture 任务，覆盖搜索、修改、测试、恢复、安全和上下文。
- [ ] 17. 将 eval 任务拆分为开发集与 held-out 测试集，降低针对样例过拟合的风险。
- [ ] 18. 增加 baseline/experiment 对比命令，生成结构化 JSON 和 Markdown 实验报告。
- [ ] 19. 将确定性离线 eval 接入 CI；真实 Claude API smoke test 通过环境变量显式开启。
- [ ] 20. 为实验结果增加置信区间，并区分 Agent 失败、grader 失败和基础设施失败。

### 阶段三：Harness 与 Runtime 可靠性

- [ ] 21. 将 evaluator 改为可配置 grader registry，移除“任务是否提到测试”作为核心成功判断。
- [ ] 22. 支持任务级验收标准和任务专属测试命令。
- [ ] 23. 增加任务状态机：pending、running、passed、failed、blocked、skipped、cancelled。
- [ ] 24. 支持任务依赖；前置任务失败时阻止错误的后续执行。
- [ ] 25. 增加最大 API 调用数、工具调用数、token、耗时和可选成本预算。
- [ ] 26. 增加 checkpoint/resume，中断后从最后一个一致状态继续。
- [ ] 27. 根据 `error_type` 路由 repair 策略，只自动重试可恢复错误。
- [ ] 28. 为重试增加最大次数、退避策略和重试原因记录。
- [ ] 29. 修复超时执行的进程终止语义，避免返回 timeout 后后台任务继续产生副作用。
- [ ] 30. 为可能产生副作用的工具设计幂等保护和重复调用检测。
- [ ] 31. 并行执行互不依赖的只读工具，并保证输出顺序确定、并发数可控。
- [ ] 32. 对顺序执行与只读并行做成功率、耗时、token 和错误率消融实验。

### 阶段四：Memory 与 Context 科研优化

- [ ] 33. 将 ContextBuilder 接入 AgentLoop，并记录每条注入上下文的来源与选择原因。
- [ ] 34. 从消息数和字符预算升级为 token-aware context budget，保持 tool_use/tool_result 配对完整。
- [ ] 35. 实现路径、symbol、关键词、最近任务和工程决策的混合检索排序。
- [ ] 36. 基于 AST 增加 import、symbol 和调用关系，支持依赖文件与 edit-ripple 上下文发现。
- [ ] 37. 建立上下文检索 gold 数据集，计算 Recall@K、Precision@K、MRR 和 token 占用。
- [ ] 38. 对关键词、混合排序和关系图检索做消融实验，并关联端到端任务成功率。
- [ ] 39. 增加 Memory 来源、时间、指纹、置信度、去重和过期策略，降低陈旧或失败记忆污染。

### 阶段五：安全边界

- [ ] 40. 建立 workspace 安全攻击集，覆盖 symlink、硬链接、重定向、glob、环境变量、命令替换和 allowlist 前缀绕过。
- [ ] 41. 改进 Bash 命令语义解析和精确 executable allowlist，降低字符串前缀误判。
- [ ] 42. 设计可选 OS sandbox adapter，在 macOS、Linux 或容器环境提供文件系统与网络隔离。
- [ ] 43. 为 permission allow 增加作用域、有效期、持久化、查看和撤销能力，并写入审计事件。

### 阶段六：工程交付成熟度

- [ ] 44. 增加 TOML 配置、配置 schema、未知字段报错、示例配置和运行时配置快照。
- [ ] 45. 拆分过大的 CLI 命令处理逻辑，保持现有命令和输出兼容。
- [ ] 46. 抽象稳定的 ModelClient 协议，移除硬编码 `max_tokens`，集中管理模型能力和请求参数。
- [ ] 47. 提供版本化结构化报告，并预留可选 OpenTelemetry Agent/Workflow/Tool span 导出。
- [ ] 48. 明确 Python 版本下限、依赖锁策略、Gitee CI、构建 smoke test、版本号和 changelog 发布流程。

## 5. 暂缓项

以下能力只有在前置 eval 能证明价值后再排期：

- 向量数据库和 embedding 检索。
- 复杂多 Agent 协作与 Agent 团队调度。
- Web UI、Dashboard 和远程控制面板。
- 完整 MCP Server 或工具市场。
- 多模型供应商适配。
- Agent 自动 commit、push 或合并远程分支。

暂缓不代表永远不做，而是避免在缺少基线时增加难以验证的复杂度。

## 6. 单次小推进的交付协议

用户说“帮我做一个小的推进”时，默认执行以下流程：

1. 选择队列中第一个未完成项。
2. 检查当前分支、远端同步状态和已有用户改动。
3. 读取仓库要求的开发规范；涉及日志或合同期限时读取对应专项规范。
4. 明确最小改动范围和验收标准。
5. 先写失败测试，再写最小实现。
6. 运行相关单测，并运行全量 unittest、mypy、ruff；按风险补充 build 或 E2E。
7. 更新本路线图状态、相关模块文档和必要的工程变更记录。
8. 检查 diff，排除 `.DS_Store`、`output/`、`tmp/`、本地 lock 或其他无关产物。
9. 提交并推送到 `origin/master`；禁止 force push。
10. 返回提交哈希、验证结果、改动摘要和下一项任务。

如果远端出现新提交、工作区存在冲突、需要破坏兼容性或任务规模明显超过一个小提交，则停止推送并先说明原因。
